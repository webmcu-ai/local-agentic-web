### 4. COMMON AGENT CONTROLLER

Implement a provider-independent agent controller.

Separate these responsibilities:

- Model communication.
- Conversation and task state.
- Tool-call parsing and validation.
- Tool execution.
- Workspace management.
- Permission checks.
- User-visible event logging.
- Final response rendering.

Use explicit states, for example:

`idle`, `connecting`, `thinking`, `tool_requested`, `awaiting_approval`, `executing_tool`, `streaming`, `completed`, `cancelled`, and `error`.

Display the current state clearly.

Implement a bounded tool-use loop:

1. Send the current conversation and available tool definitions to the selected provider.
2. Collect the model response.
3. Determine whether it contains a valid tool call or a final answer.
4. Validate the requested tool and its arguments.
5. Check whether the tool requires user approval.
6. Execute the permitted operation.
7. Record the tool result.
8. Return that result to the model in the appropriate conversation format.
9. Continue until the model finishes, the user cancels, an error occurs, or the iteration limit is reached.

Make the maximum number of tool iterations configurable, with a conservative default such as 8.

Prevent infinite loops, duplicate execution of the same request, unbounded response growth, and uncontrolled concurrent runs.

Provide a Stop button that cancels the active model stream and prevents further tools from running.

Never execute arbitrary JavaScript, `eval()` strings, shell commands, or model-generated functions.

The model must request tools through a defined structured protocol. The browser application—not the model—decides which operations are permitted.

### 5. STRUCTURED TOOL-CALL PROTOCOL

  "type": "tool_call",

  "name": "read_file",
  "arguments": {

  "content": "The sketch initializes the ESP32 pins..."

The application must validate JSON structure, tool names, argument types, required fields, file paths, and output limits.

Do not execute incomplete JSON emitted during streaming. Buffer the response until a complete, valid tool request can be parsed.

Do not rely exclusively on regular expressions to extract tool calls from arbitrary prose.

- `propose_file_edit`
- `get_workspace_summary`
- `inspect_esp32_pin_map`
- `get_serial_status`

Add additional tools only when they have a clear purpose and reliable implementation.

A tool error should become a structured result that the model can use to recover. Never represent a failed operation as successful.
