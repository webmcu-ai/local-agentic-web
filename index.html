⚠ First-time setup — click to expand
▼ show

Ollama must be installed and running locally. This page calls localhost:11434 directly from your browser.

1
Download and install Ollama from ollama.com
2
Allow browser access. Once Ollama is installed, open a command window.

On Windows, run:
setx OLLAMA_ORIGINS "https://webmcu-ai.github.io"
On Mac/Linux, run:
export OLLAMA_ORIGINS="https://webmcu-ai.github.io"
Note: this address points to the webmcu-ai GitHub organization. If you are hosting this page from your own GitHub account or organization instead, replace https://webmcu-ai.github.io with your own GitHub Pages address before running the command.
3
Windows only: reboot your computer. The environment variable does not take effect until after a full restart. (Mac/Linux: the export command takes effect in that terminal session right away — no reboot needed.)
4
After rebooting, wait for Ollama to start and show its icon in the system tray (Windows) or menu bar (Mac). Then load the installed PWA. Return here — the status pill top-right will turn green when connected.
5
Pull a model using the field below, or run this in a terminal:
ollama pull gemma4:12b
Note: Ollama model tags use size shorthand — gemma4:e2b, gemma4:12b.
ℹ How this works — click to expand
▼ show

Nothing to install. The model runs entirely inside this browser tab via WebGPU — no server, no localhost calls, works offline once cached.

1
Your browser needs WebGPU support (recent Chrome, Edge, or a Chromium-based browser on desktop; Firefox/Safari support is still landing). If the engine fails to compile, that's the most likely reason.
2
Pick a model below and click Compile & Instantiate Local Engine. The first run downloads the weights (can be a large file) and caches them in this browser's IndexedDB storage.
3
On later visits, an already-downloaded model loads straight from that local cache — no network needed. Cached models are listed under "Cached locally" below, the same way the Ollama tab lists models it has installed.
4
The status pill top-right shows engine state (uninitialized / compiling / ready) instead of a server connection, since there's no server to check.

📁 Agentic Folder Automation (Local, Zero API-Token Loop)
▼ show
Help: how this panel works, multi-file output, file variables
"Select / Create Agent Folder" needs one click (browser security requirement for showDirectoryPicker). After that, everything below — reading files, calling Ollama, writing outputs, chaining passes — runs with no further clicks, driven by an interval loop. Reloading the page will require one more click to re-confirm folder permission; that's a browser-enforced limit, not something JavaScript can route around. Each request goes through whichever backend is selected top-right — the local Ollama server at http://localhost:11434, or the in-browser WebGPU engine once it's compiled — using the Model / System Prompt set above.
When checked, the model's response is scanned for markers like this and each block is written to its own file (subfolders like css/style.css are created automatically): 
=== FILE: index.html ===
<!DOCTYPE html>...

=== FILE: css/style.css ===
body { ... }

=== FILE: script.js ===
console.log("hi");
Your base prompt below needs to actually instruct the model to respond in this format — the toggle only controls how the response gets parsed, it doesn't change what the model writes. If no markers are found in a response, it falls back to writing the whole thing as one file. The three names above are just an example of the marker syntax — the parser doesn't care what the names are or how many files there are. If you want the model to invent its own filenames and file count, say so explicitly in the base prompt; it won't do that on its own just because the toggle is checked. Click "Load creative example" below for a starter prompt written that way.
File variables: write ${input}, ${filename}, ${iteration}, ${original}, or ${manifest} anywhere in the prompt above to reference the file currently being processed. Any other ${name} is looked up against the other files sitting in the folder right now — e.g. ${sensor1} pulls in the live content of sensor1.in.txt.
${original} is special: on first processing, each job's starting content is snapshotted once to <name>.backup.input.txt (never overwritten again). ${original} always resolves to that snapshot, so even after many auto-chain passes have overwritten the live .in.txt file, the model can still see what it was originally asked to do — e.g. Original request: ${original}\nLatest draft: ${input}\nImprove the draft while staying true to the original request.
${manifest} is for additive multi-file chains ("make one more file each pass"): it lists every file this job has written so far (<name>.manifest.txt), so the model can be told what already exists and add something new instead of re-generating or overwriting it. When multi-file output + auto-chain are both on, the live .in.txt is deliberately left untouched pass to pass (see the "Load Creative Multi-File Example" button) — progress is tracked via ${manifest} + ${iteration} instead of mutating the input.
